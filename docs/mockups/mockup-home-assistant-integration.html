Settled decisions

What this mockup fixes, why, and what each choice costs the people who build it. Anything not listed here is still open.

01One connector row per home, never one connector with many URLs

Two homes have different tokens, different admin rights, different network reachability, and different urgency. Folding them into a single connector would force every setting to be either global or per-home-with-exceptions. Each instance gets its own row, health badge, sources, push-delivery rule, and polling interval.

Connector storage keys on instance ID, not connector type. The Settings list can show n Home Assistant rows, and health is computed per row.

02Instance attribution rides on every notification

A name chip with a colour dot sits in the card meta row and repeats in the detail header. Colour never carries the meaning alone — the home's name is always spelled out, so the chip survives greyscale, colour blindness, and a screen reader.

Notifications need a stable instanceId and instanceLabel; renaming an instance must rewrite labels on open notifications, not only new ones.

03Four sources, each independently switchable

Device alerts, Updates, Persistent notifications, and Repairs answer different questions and have different noise profiles. Each row states what it covers, how many entities currently match, and which notification levels it can produce, so the choice is made on evidence rather than on the label.

The polling job must be able to skip whole endpoint families. Matched-entity counts come from the last successful test or sync and need a cached value for the pre-save state.

04Only a confirmed non-admin token locks a source; an unknown answer locks nothing

Home Assistant long-lived tokens inherit the creating account's permissions and cannot be scoped down. A non-admin token can read states but cannot see Updates or Repairs. Hiding those toggles would make a permissions problem look like a missing feature, so they stay visible, disabled, and labelled with the reason and the fix. An unreachable instance or a rejected token is a different answer: nothing was read, so nothing is locked and nothing is claimed — the panel says source availability is unknown and keeps the choices already made. No help text ever tells you to switch on a control that is disabled.

Test connection must report admin capability separately from reachability, and the connector must persist a capabilities record with a tri-state — confirmed, denied, unknown — so a failed probe never silently downgrades a working configuration. Permission-denied is a first-class action outcome, not a generic failure.

05Test connection reports findings, not a green tick

A successful probe names the Home Assistant version and counts what it found: matched entities, update entities, open repairs, persistent notifications. That turns an abstract "connected" into a preview of the noise you just signed up for. Each of the four outcomes — connected, unreachable, token rejected, connected-but-not-admin — resolves to exactly one health badge, one source posture, and one next move. They are mutually exclusive by construction: an unreachable instance never also reports a permissions verdict.

The test endpoint does more than one call and needs a bounded timeout with a partial-result shape, because a reachable instance with a valid non-admin token is a success and a warning at the same time — while a transport failure is neither and must not be reported as one.

06Every update stays independent; push summaries reduce interruptions

Each update is always its own Mission Control notification, with its own action and reconciliation lifecycle. Daily summary is only an outbound push preference: one device interruption can open the filtered list of six individual updates. Security updates and the named Core/OS entities still push immediately, so batching never delays the one update that mattered.

Summary scheduling is per instance and needs the household's timezone, not the server's. The summary is a delivery event, never a grouped inbox record. Overrides are matched by entity ID, and installing directly in Home Assistant resolves only that entity's notification on the next poll.

07Polling interval is stated as a delay, not as a frequency

"Every 15 minutes" hides the consequence. The hint states it plainly: a door left open is reported at most 15 minutes late. The request count per day is shown alongside so the cost of a tighter interval is visible in the same glance.

Mission Control polls the REST API and does not hold a websocket, so worst-case latency equals the interval. If push ever lands, this copy and this control both change meaning and must be revisited.

08Anything that changes the house confirms in one shared dialog

Install update, skip a version, ignore a repair, dismiss at source, mute an alert, and removing an instance all route through a single modal: named consequence, named home, Cancel focused first, Escape to back out. Install adds the version it is on and the version it is offered, plus an unchecked Create a backup first when Home Assistant supports one for that entity — and says so plainly when it does not. Create task and Open in Home Assistant act immediately, because they change only Mission Control or nothing at all.

Actions need a confirm descriptor with its own copy per event type, and update payloads must carry both versions and a backupSupported flag. One dialog component serves every surface: while it is open the triggers underneath are inert, so a confirmation can never be raced by a second click on the card behind it.

09"Accepted" and "confirmed" are separate states, and the copy never conflates them

Mission Control polls; it does not watch. So a write-back has two truths: Home Assistant took the request, and a later poll saw the result. The card says started installing … still running 2025.8.1 until a poll confirms it finished and offers Check for confirmation now. Only after that does it say installed, move into Resolved today, and drop out of the open count. From the moment an action starts until it settles, every write-back on that card and in its detail pane is withdrawn from both surfaces, so the same change cannot be sent twice; Open in Home Assistant stays. A confirmed Install or Skip is never offered again. Failures and refusals state what did not change and carry the single recovery path in the state line — Retry, or a fix for the credential — so the same action is never offered twice on one card.

Extends the shipped WritebackStatus with an accepted-but-unconfirmed state; pending must survive a refresh, and reconciliation needs to close the loop from the next poll rather than from the write response. Retryable and terminal failures must be distinguished at the API layer.

10Stale and resolved are different, and both are honest

When an instance stops answering, its cards dim, every write-back that would touch that home is withdrawn, and a banner states when it last responded — a door alert from 14 minutes ago may already be wrong. Only that home is affected: the other homes keep their live cards and their full action sets in the same list. When the underlying condition clears at the source, the card resolves itself and says who cleared it, instead of quietly disappearing.

Notifications need a last-observed timestamp separate from created-at, and reconciliation must be able to close a Mission Control notification because the source condition disappeared.

11Cards use full tinted borders, not a coloured left stripe

The shipped NotificationCard marks level with a 3px left border. DESIGN.md's Complete Container rule forbids partial coloured edges, so this mockup carries level on a full 1px tinted border plus the level pill and level icon. That is a deliberate deviation from current code toward the written spec.

Adopting this treatment for Home Assistant alone would split the notification list visually. Either the existing card changes with it, or this decision is reversed before build — it should not ship half-applied.

12Adding a second home starts empty and validates before it can save

"Add another Home Assistant" inserts a draft row and clears the editor rather than cloning the first home, because a copied token pointed at a new URL is a silent failure. Save stays disabled until the URL has a scheme and the token is present; errors name the problem and the fix on the field itself.

The draft row exists in the list before it is persisted, so the list must tolerate an unsaved instance and Cancel must remove it cleanly.

13The two-pane list keeps its own scroll; below 1000px it stops being two panes

On a wide screen the list and the detail pane are independently scrollable inside a shared, bounded height, so reading down a long list never strands the reader beside an empty detail column. Between roughly 720px and 1000px there is not enough width for two readable columns, so the layout stacks — detail below list — rather than squeezing both. At 320px the card still leads with its home, and the primary action is reachable without a horizontal scroll.

The notification surface needs a container-bounded height rather than page flow, and the stacked breakpoint must select the detail pane into view on tap. Three layouts get tested, not two: stacked mobile, stacked tablet, and side-by-side desktop.

All data in this artifact is synthetic. Hostnames use reserved example domains, the token string is a non-functional placeholder, and every version number, entity ID, and timestamp is invented for review. No external fonts, scripts, styles, or images are loaded — the file renders offline exactly as it renders online.
