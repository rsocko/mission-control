Product research · 5 August 2026

Linear inspiration,
Mission Control fit

A prioritized review of what to refine, add, defer, and avoid. The central conclusion: Mission Control already owns much of the right substrate. The opportunity is to make its project intelligence more visual, explainable, connected, and fast—not to import Linear's team-management ceremony.

Finding 01
Refine

Computed health, project tags, phases, dependencies, percentile metrics, triage, and command UX already exist in partial form.

Finding 02
Separate

Keep the task due-date calendar. Add a distinct projects-only portfolio roadmap rather than forcing one timeline to serve two jobs.

Finding 03
Infer

Use Linear's visual language for health, but preserve MC's principle of deriving state instead of requiring weekly written updates.

Prioritized assessment

P0.1

Explainable Project Pulse

MC already separates inferred lifecycle status from computed health. Upgrade the display and model with reason codes, freshness, trend, confidence, and one suggested intervention. “Pulse” should be MC's name for an inferred state, not represented as a verified Linear feature.

High value · low/medium lift
P0.2

Wire project tags end to end

The project_tags table and overview read path already exist, but project create/edit and APIs do not expose tag assignment. Keep category as the primary portfolio grouping; add tags for themes, goals, contexts, and integration provenance.

High value · low lift
P0.3

Portfolio roadmap timeline

MC's current Timeline is a monthly task due-date calendar. Build a separate projects-only roadmap using existing project target dates, phases, milestones, dependencies, category, tags, and health. Add day/week/month/quarter zoom and milestone-to-project promotion later.

High value · medium lift
P1.1

Drillable scatter insights

MC already has lead-time median/P85/P95, distributions, trends, outlier links, and age-bucket drilldowns. Add per-task scatter as another rendering of the same data and filters—not a new analytics subsystem.

Medium/high value · medium lift
P1.2

Command palette scopes + actions

Build on Ctrl+K hybrid search, quick-create parsing, slash search, and existing G-chords. Add visible scopes for tasks, projects, tags, sources, and commands; make every shortcut discoverable in the palette.

Medium value · medium lift
P1.3

Unify inbound triage semantics

MC already has a rich content triage system, connector-created tasks, notifications, and Scout ingestion. Standardize accept, dismiss, snooze, merge/duplicate, and route actions across them instead of creating a second Linear-like inbox.

Medium value · medium lift
P1.4

Integration platform before catalog

MC already exposes MCP, inbound/outbound webhooks, n8n, custom REST, and connector capabilities. Invest in observability, provenance, conflict handling, and a few deeper workflows rather than chasing Linear's logo count.

High leverage · ongoing

Copy cautiously / avoid

Manual project updates
A weekly narrative ritual makes sense for stakeholder reporting, not a solo command center. Generate the narrative from signals and let the user annotate only exceptions.
Initiatives as a default entity
Category + project tags + smart views cover the current need with less ceremony. Add an objective entity only after real multi-project rollup pain appears.
Cycles, SLAs, and team rituals
These optimize shared accountability. MC's personal countdowns, due dates, energy, and focus signals are the better-sized analogs.
Full collaboration suite
Co-editing, reactions, update reminders, and subscriber systems are disproportionate unless MC becomes multi-user.
Fragmented filter models
Do not create separate filter semantics for pages, quick filters, and insights. One filter state should drive lists and visuals.

Important correction to the premise

No current public Linear feature named “Pulse” was verified. Linear does verify separate project status and health attached to manually authored project/initiative updates. The useful inspiration is the visual and conceptual separation; the MC-specific innovation is to infer it and explain why.

Answer: “Is Initiative our category or tags?”

Neither maps perfectly. In Linear, an Initiative is a first-class strategic objective containing a curated set of projects. MC's category is a primary grouping; tags are flexible cross-cutting metadata. For MC today, category + project tags + saved/smart views recreate most initiative value with less ceremony.

Decision rule: Add an Initiative entity only when the user needs objective-specific ownership, narrative/resources, a target date, and historical rollup across projects—not merely another way to group them.

Current implementation gap

Project tags are not hypothetical: storage and overview reads already exist. The missing surfaces are write APIs, the project editor picker, display/filter affordances, and tests. This is a high-confidence, low-risk improvement.

Worth considering next

Deepen: GitHub PR/issue/project lifecycle; M365 Planner through Scout or a direct connector; browser/mobile capture; Sentry or equivalent only for actionable incidents; MCP permissioning and project tools; webhook templates for common sources.

Lower priority / avoid

Slack-style broadcast updates, Salesforce/customer-request machinery, Figma issue creation, release orchestration, and dozens of thin point connectors unless a concrete personal workflow demands them.

Linear lesson worth copying

Preserve structured provenance when an external item becomes work: source object, source conversation, sync direction, connector capability, and last reconciliation state. Do not flatten every integration into title + URL.
